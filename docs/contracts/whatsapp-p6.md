# P6: WhatsApp via OpenWA (hand-off + record, admin-only)

> Status: contract v1, written by the orchestrator before P6 fans out. Tracks: **spine** (schema, models, enums, Data, events, policy, client interface), then **6A** backend, **6B** UI,
> **6C** mock/ops/e2e infrastructure. Facts about OpenWA: [../whatsapp-openwa.md](../whatsapp-openwa.md) (verified summary) and
> [../reference/openwa-api.md](../reference/openwa-api.md) (full API reference). Plan sections 3 and 6.5 are the origin of the decisions below.

## Settled decisions

- **P6-D1 admin-only everywhere.** Every WhatsApp surface (settings page, inbox, API routes, Inertia props, search, export, realtime channel, nav entries) is admin-only: `is_admin` and an active account. Agents get `403` (API/pages) and see nothing in the UI; the Reverb channel `private-whatsapp-admin` is registered for admins only (it is deliberately unregistered in P4). A dedicated middleware alias `wa.admin` and `WhatsAppPolicy` enforce it explicitly (the `Gate::before` bypass of admins is fine here, but an agent must never pass: test every route with an agent, a plain visitor token and a guest).
- **P6-D2 separate domain.** WhatsApp chats never join `conversations`/`messages`; tables `whatsapp_sessions`, `wa_handoff_tickets`, `wa_chats`, `wa_messages`, `wa_webhook_deliveries` (migration block `2026_11_25_*`). A `wa_chat` may be LINKED to a widget/visitor/category through a hand-off ticket; the visitor never sees WhatsApp history through the widget (hand-off + record only).
- **P6-D3 hand-off.** The visitor panel's channel chooser (shown only when `availability.whatsapp.enabled && features.whatsapp`) calls `POST /api/v1/public/widgets/{key}/whatsapp-handoff {category?}` (visitor bearer, same gates as chat start, own limiter) and gets `{ code, waUrl, expiresAt }`: an 8-character code from the alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no 0/O/1/I/L), `waUrl = https://wa.me/<digits of the connected number>?text=<urlencoded "Hi! My support code is K7M2QX">`, ttl `whatsapp.handoff_ttl_minutes` (default 1440). `ChatLinker` matches a live ticket code in the first inbound messages of a `wa_chat` (case-insensitive, word-bounded) and links widget/visitor/category; an unmatched chat is still recorded; groups are ignored by default (`whatsapp.ignore_groups`, default true).
- **P6-D4 webhook.** `POST /webhooks/openwa/{session_ulid}` (routes/webhooks/whatsapp.php, the bearer-only `widget` group: no session, no CSRF, no cookies): verify `X-OpenWA-Signature: sha256=<hex>` = HMAC-SHA256 of the RAW request body with that session's webhook secret (constant-time, before anything else; missing/invalid -> `401` with a generic body, no hint), dedupe on `X-OpenWA-Idempotency-Key` (fallback `X-OpenWA-Delivery-Id`) through `wa_webhook_deliveries` (unique), answer `200` quickly and process through the queue; body size cap; named limiter; unknown session ulid -> `404`; replays and duplicates are `200` no-ops. Events handled: `message.received`, `message.sent`, `message.ack`, `message.failed`, `session.status`, `session.qr`, `session.authenticated`, `session.disconnected`, `session.reconnect_loop`; everything else is acked and ignored. The parser is tolerant (the raw JSON is kept; unknown fields never fail a delivery).
- **P6-D5 outbound.** Only admins reply (`POST /api/v1/whatsapp/chats/{ulid}/messages {body}`) through `OpenWaClient::sendText`; protections against bans: replies only to chats that were inbound-initiated (`whatsapp.reply_only_to_inbound`, default on), a minimum interval between sends per session (`whatsapp.send_min_interval_ms`), a daily cap per session (`whatsapp.daily_send_cap`), `429 SEND_PACING_LIMITED` from OpenWA is retried with backoff; `201` from OpenWA means accepted, not delivered: the message row is `pending` -> `sent`/`delivered`/`read`/`failed` as `message.ack`/`message.failed` webhooks arrive.
- **P6-D6 sessions.** Admin creates/starts/stops/deletes WhatsApp sessions through OpenWA from the settings page; QR polling (`GET /api/sessions/{id}/qr`) until `ready`; a status machine `created -> starting -> qr -> ready -> disconnected|failed`; the webhook is registered at start with a per-session random secret and `events[]` above; OpenWA rejects private webhook URLs unless `SSRF_ALLOWED_HOSTS` allows the app host (documented, with a clear error in the UI). The OpenWA base URL and API key are settings (`whatsapp.openwa.base_url`, `whatsapp.openwa.api_key` encrypted; never returned by any API; a connection test endpoint).
- **P6-D7 media.** Inbound images (<= 1 MiB inline `data`, larger ones are `omitted`: fetch through OpenWA's media endpoint) are stored on the private disk after the P4 `ImageSanitizer` (re-encode, size/dimension limits); documents/audio/video/stickers are recorded as typed rows with filename/mime/size and no stored file in P6 (shown as "attachment not stored").
- **P6-D8 realtime.** Domain events -> `private-whatsapp-admin` broadcasts (`wa.message.created`, `wa.chat.updated`, `wa.session.status`), `v: 1`, admin-only payloads; failures never break the webhook response.
- **P6-D9 widget.** `features.whatsapp` already exists in the widget config; the builder gets the WhatsApp section (channel on/off, which session's number is shown, the hand-off text); `availability.whatsapp.enabled` becomes true when a `ready` session is linked to the widget.
- **P6-D10 testing.** A mock OpenWA server (6C) reproduces the recorded real-image shapes; the real OpenWA image runs in Docker (`docker compose -f docker/compose.dev.yml --profile whatsapp up -d openwa`) to record fixtures for session create/start/QR/webhook registration and error shapes; a real device round trip needs the user's phone (documented, not automated).
