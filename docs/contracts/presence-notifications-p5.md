## Decisions (settled)

- **P5-D1 presence storage**: `PresenceService` keeps its public API and the three REST endpoints; storage moves behind `App\Domain\Presence\Contracts\PresenceStore` with `RedisPresenceStore` (default when `config('presence.store') === 'redis'`, which defaults to `redis` when `CACHE_STORE`/`QUEUE_CONNECTION`/`SESSION_DRIVER` is redis, else `database`) and the current `DatabasePresenceStore`. Redis: one hash per user (`presence:{id}`: status, manual, visible, last_heartbeat_at) with a TTL of 2 x the heartbeat window, plus a ZSET `presence:alive` scored by last heartbeat for the sweep and roster. The `agent_presence` row is a MIRROR written only when the EFFECTIVE status changes (not on every heartbeat), so heartbeats cost no SQL.
- **P5-D2 effective status**: the staff host beats every 30 s with `POST /me/presence/heartbeat {visible: bool}` (background tabs are throttled by browsers to about once a minute, which still fits the 90 s window). A manual choice wins (`offline` stays offline, `away` stays away, `online` stays online while fresh); without a manual choice: no heartbeat for 90 s = `offline` (closed tab, sleeping laptop); fresh heartbeats with `visible=true` = `online`; fresh heartbeats that have all reported `visible=false` for `presence.auto_away_minutes` (default 5) = `away`, and the next `visible=true` beat makes the agent `online` again. Routing eligibility (`online` or `away` and fresh) is unchanged from P4; wave 1 is `online` only, so an auto-away agent is offered chats in wave 2.
- **P5-D3 sweep**: `chat:presence-sweep` runs every minute (scheduler), marks stale users `offline`, dispatches `PresenceChanged` once per real change, drops the cached widget availability when reachability flips, and is idempotent/overlap-safe (`withoutOverlapping`, `onOneServer`).
- **P5-D4 push (Web Push)**: VAPID keys already exist (`chat:bootstrap-secrets`). Tables (block `2026_11_20_*`): `push_subscriptions` (user_id, endpoint_hash unique, endpoint (text), p256dh/auth encrypted, user_agent, created/last_used/expires), `notification_settings` (user_id unique; `sound` bool default true, `push_offers` bool default true, `push_messages` bool default true, `quiet_hours` json {enabled,start,end,timezone}, `prompted_at`, `prompt_state` enum `never|granted|denied|snoozed`, `snoozed_until`), `device_tokens` (FCM stub: user_id, platform, token hash/encrypted, last_seen). A `PushChannel` interface with `WebPushChannel` (via laravel-notification-channels/webpush / minishlink) and a `FcmChannel` STUB that logs and returns "disabled" (`config('push.fcm.enabled')=false`); everything is queued, a dead subscription (404/410) is deleted, failures never affect the HTTP request.
- **P5-D5 what is pushed**: `ChatOffered` -> each offered agent whose settings allow `push_offers`, outside quiet hours, and who has NO visible dashboard heartbeat in the last 60 s (an agent looking at the inbox gets toast + sound, not an OS notification); tag `offer-{conversationUlid}`, TTL = remaining offer time, urgency `high`. `ChatTaken`/claim/cancel/expiry -> a SILENT push of type `dismiss` with the same tag so the notification disappears on the agents' devices. A visitor message in a chat assigned to an agent who is not looking (no visible heartbeat) -> push (setting `push_messages`), tag `chat-{ulid}`. Payload is small and E2E-encrypted by the push protocol: title (e.g. "New chat request"), body (category + a <= 120 char preview of the first message, setting `notifications.push_include_preview` default true), `data.url` (`/inbox/{ulid}` or `/inbox`), `data.tag`, `data.type`. No integer ids, no e-mails.
- **P5-D6 service worker + manifest**: `public/sw.js` (scope `/`, no caching, no fetch handler): `push` (show with tag/renotify, or close on `dismiss`), `notificationclick` (focus an existing dashboard client and navigate it, else open the URL), `pushsubscriptionchange` (re-subscribe, POST the new subscription). `public/manifest.webmanifest` (name/short_name from the app name setting is NOT possible in a static file: serve it from a route `GET /manifest.webmanifest` generated from settings, with icons 192/512 PNG + maskable + `apple-touch-icon` already in `public`), linked from the root view; iOS needs an installed PWA (documented caveat).
- **P5-D7 permission flow**: never ask on page load. After a staff member's first sign-in (no `prompt_state`), show an in-app explainer dialog ("get notified of new chats even when this tab is closed"); only the button click calls `Notification.requestPermission()`, then subscribes (`pushManager.subscribe({userVisibleOnly: true, applicationServerKey})`) and POSTs the subscription. "Not now" snoozes 7 days. A `denied` state is shown in Settings > Notifications with instructions. Browsers without Push/Notification support (older iOS Safari tabs) fall back to in-tab toast + sound + title badge and the settings page says why.
- **P5-D8 in-tab notifications**: when permission is granted and the dashboard tab is hidden/unfocused, an offer shows an OS notification from the page (same `tag` as the server push so the browser replaces, never doubles); when focused: toast + sound only (setting `sound`). The wrapper from 4C (`lib/realtime/staff/os-notification.ts`) is extended, not replaced.
- **P5-D9 API** (management group, any staff): `GET/PUT /api/v1/me/notification-settings`, `POST /api/v1/me/push-subscriptions` (upsert by endpoint hash), `DELETE /api/v1/me/push-subscriptions/{id}`, `GET /api/v1/me/push-subscriptions`, `POST /api/v1/me/push-subscriptions/test` (sends a test push to the caller's subscriptions), `POST /api/v1/me/devices` + `DELETE` (FCM stub). Shared Inertia prop `push: { vapidPublicKey } | null` (null when VAPID is not configured). Settings page `/settings/notifications`.
- **P5-D10 launcher alert**: the launcher already shows an unread badge (`unread` message from the panel, `unread-changed` event). 5C verifies the whole chain with the real panel (the iframe stays alive and connected while the bubble is closed), adds the closed-bubble reply alert (shake/pulse, respects `prefers-reduced-motion`, optional sound when `features.sounds`), clears the badge on open, handles several quick replies, and keeps the badge consistent across page navigations (the panel rebuilds the unread count from the server's receipts on boot: the messages fetched on resume carry `seen_at`; the alert is coalesced to one per 8 s, deferred while the tab is hidden and remembered across tabs and pages through the host key `chatfeature:<publicKey>:alert` = `{at, n}`). The loader budget is raised to **18 KB gzip** (decision; `.size-limit.json`, `build.test.ts`); keep it as small as reasonable.
- **P5-D11 history search/export (plan 5C)** was delivered in P4 (admin history with filters/search, streaming CSV/JSON): nothing to do except an e2e/perf check on a large export, if time permits.

## Test notes

Redis is available locally (tests that need it use a dedicated key prefix and a dedicated Redis database index, never `FLUSHALL`; skip cleanly when Redis is unreachable). Real push delivery cannot be exercised without the vendors' push services: tests use the `WebPush` fake/`Http::fake` for the server and, in e2e, a granted `notifications` permission plus the Chrome DevTools Protocol (`ServiceWorker.deliverPushMessage`) to drive `sw.js` for real.
