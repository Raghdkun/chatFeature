# REST API

> Status: the P3 endpoints (public widget config/availability; management of categories, agents and widgets) are **implemented and reviewed**; the P4 chat endpoints (visitor sessions and chat, staff conversations, presence) are **implemented** (track 4A, see "Chat API (P4)" below; the realtime events they trigger are track 4B), hardening and the generated reference (Scribe is installed as a dev dependency; its `/docs` route is removed with `composer install --no-dev`) are P7. Exact shapes and error codes: [contracts/rest-shapes.md](contracts/rest-shapes.md) and [contracts/dashboard-pages-p3.md](contracts/dashboard-pages-p3.md).

Everything lives under a versioned `/api/v1`. One API serves the web dashboard and a future mobile app. Two Scribe configs are planned (management, public). Paths marked "P3" or listed under "Chat API (P4)" exist today; the rest are **draft** except where marked "plan" (named explicitly in the plan).

## Conventions

| Topic | Rule |
|---|---|
| Versioning | URL-versioned: `/api/v1` |
| Error shape | `{"error":{"code":"...","message":"...","details":{}}}` for every `api/*` response (a 500 in production is `server_error`); the pre-install `503 not_installed` is a bare `{"error":"not_installed"}` |
| Known codes (P3) | `validation_failed` (422), `unauthenticated` (401), `forbidden` (403), `not_found` (404), `rate_limited` (429, `Retry-After`), `widget_not_found` (404) and `origin_not_allowed` (403) on the public widget endpoints, `category_in_use`, `slug_taken`, `managed_by_auth_portal`, `cannot_deactivate_self`, `not_an_agent` (all 409), `auth_unavailable` (503, auth portal down beyond the grace window), `session_revoked` (401), `no_chat_access` (403), `auth_mode_unavailable` (500, `auth.mode` missing on an installed instance), `server_error` (500) |
| Known codes (P4) | `no_agents` (`details.target` / `details.reason` on a transfer), `conversation_exists`, `already_claimed` (`details.by` = the winner's name), `at_capacity`, `conversation_not_active`, `conversation_not_live`, `conversation_not_queued`, `conversation_not_ended`, `conversation_not_open`, `already_rated`, `rating_window_closed` (all 409, see the chat section), `attachment_quota_exceeded` (422, `details.file`), `feature_disabled` (403: the widget switched the feature off), `rate_limited` (429, `Retry-After`; also for the chat-start guards below, `details.retry_after`) |
| Pagination | Cursor pagination (no offsets) |
| Idempotency | `client_msg_id` for messages (unique per conversation); idempotency keys for other writes |
| Rate limiting | Named rate limiters per route group |
| IDs | ULIDs / `public_key` only; no integer ids exposed |

## Chat API (P4)

Resource shapes (`Message`, `ConversationPublic`, `ConversationStaff`, `Attachment`, `Presence`, `Rating`) are the Data classes in `app/Data/Chat` (camelCase JSON, `{ data }` envelope, ISO-8601 UTC timestamps with milliseconds), listed in [contracts/realtime-events.md](contracts/realtime-events.md) and [contracts/chat-data-p4.md](contracts/chat-data-p4.md). Request fields are snake_case. Every error uses the envelope `{ error: { code, message, details? } }`; `409` conflicts are expected outcomes the clients branch on, not faults.

### Visitor side (`/api/v1/public`, bearer `vt_...`, no cookies, no CSRF)

`POST /public/widgets/{key}/sessions` goes through the P3 gate (unknown or disabled widget `404 widget_not_found`, browser `Origin` not whitelisted `403 origin_not_allowed`, network limits) plus the `public-session` limiter. **Every other call** sends only `Authorization: Bearer vt_...` (the `visitor` middleware: `401 unauthenticated` for an unknown token, `401 session_revoked` for a revoked or expired one) and answers `404 widget_not_found` once its widget was disabled or deleted. Every `{ulid}` must belong to the token's session: **another visitor's conversation is `404 not_found`, never `403`**. A visitor never lists history: `GET /public/conversation` is the session's own latest live chat.

| Endpoint | Request | Success | Errors |
|---|---|---|---|
| `POST /public/widgets/{key}/sessions` | `{ identity_token?, visitor?: {name?, email?, phone?, meta?}, page?: {url, title, referrer}, locale? }` (all optional) | `201 { visitorToken, expiresAt, conversation: ConversationPublic \| null, ws: {key, host, port, scheme} \| null, limits: {maxMessageLength, attachmentMaxBytes, attachmentMaxDimension, attachmentMaxPerMessage} }` (the `SessionData` class), `Cache-Control: no-store`. | `POST /public/conversations/{ulid}/rating/skip` | | `200 ConversationPublic` (`closed`, reason `skipped`). Accepted for every `ended` chat inside its window whatever the widget's rating flag says | `409 conversation_not_ended`, `409 rating_window_closed` |
| `GET /public/attachments/{ulid}` | signed URL only (no token), `?thumb=1` for the 320 px thumbnail | `200` image streamed from the private disk (`Content-Type` of the stored file, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, neutral file name) | `403` (missing, altered, expired or foreign signature: `chat.attachment_url_ttl_minutes`, default 240), `404` |

**Sessions.** A signed identity makes the visitor `verified` and keyed by the token's `sub` (one `Visitor` across browsers; the claims are authoritative, the pre-chat form never overwrites them); unsigned `visitor` data is stored as given and marked unverified. A returning bearer token (an active session of the same widget) is **rotated**: same visitor, a new token (the answer is exactly that of a first session: new token and expiry, plus `conversation`, `ws`, `limits`). The previous token is not killed at once (a second tab may be mid-request) but its expiry is capped to 60 seconds from the rotation, in the same transaction, and never extended again: after that window it is `401 session_revoked`, so a stale or stolen token cannot outlive a rotation or take over a chat. This holds for the previous token of **every** rotation. A previously verified visitor is only continued with a fresh identity proof. Only a still-open live chat (`queued`, `active`) is resumed: it moves to the new session, and a session that held it (other than the token being rotated, which only keeps its overlap window and cannot reach the chat any more) is revoked at once; a visitor has at most one open live chat across all their sessions (`409 conversation_exists`). Tokens live `chat.visitor_session_ttl_days`. Unverified `meta` accumulates on the visitor across sessions, newest keys winning, capped at 20 keys and 8 KiB serialised.

**Attachments.** Judged by content (`finfo`), never by name or declared type; SVG, HTML, PDF, scripts and polyglots are refused. The compressed upload is deliberately **not** scanned for markup (legitimate photos contain such byte runs by chance); the image is decoded and encoded again and only the new bytes are stored, so EXIF, XMP, comments, trailing data and anything hidden in them (polyglots) do not survive, orientation is applied. A GIF with more than one frame is refused with `422` before it is decoded (frames are counted from the block structure: a few KB can describe gigabytes of canvas), and the decoder runs with animation decoding off, so a GIF that slipped past the scan would still decode as its first frame only. A 320 px thumbnail is made; files go to the private disk (config `chat.attachments_disk` / env `CHAT_ATTACHMENTS_DISK`, default `local`) under random paths. The signed URLs in messages are built on the configured app origin (the `app.url` setting, like snippets), never the host of the request, and live `chat.attachment_url_ttl_minutes` (default 240; chats last hours). The client's file name is kept sanitised for staff only. An upload belongs to one conversation and is referenced by one message; unreferenced uploads are deleted after 24 hours. The pictures of a message keep the order of the `attachments: [ulid, ...]` array the sender posted (stored as `attachments.position`; the order the uploads finished in does not matter), in every response and broadcast.

### Staff side (`/api/v1`, Sanctum cookie or bearer, `session.valid`, `chat.access`; limiter `staff-api`)

Visibility is `Conversation::visibleTo` for lists and `ConversationPolicy` for single conversations (called directly: `Gate::before` would let an admin through every state check). A conversation the caller may not see is `403 forbidden`. WhatsApp chats are not conversations and never appear.

| Endpoint | Notes |
|---|---|
| `GET /conversations` | Filters `status` (comma-separated), `category` (ulid or slug), `widget` (ulid), `agent` (user id or `me`), `type`, `q`, `from`, `to` (creation time), `updated_after`; `limit` (default 25, max 100) and the opaque `cursor` (a hand-made one that decodes but is not ours is `422 validation_failed` on `cursor`; junk that does not decode is no cursor); newest first. `{ data: ConversationStaff[], meta: { next_cursor } }`. `q` is the search of the admin history page (`ConversationSearch`): part of the ticket number, the visitor's name / e-mail / phone (`LIKE`), or message text (MySQL / MariaDB FULLTEXT, boolean mode, every word a prefix and all required; `LIKE` on SQLite and for words under 3 characters). Times are instants: an offset (`...+03:00`) is honoured, `updated_after` is inclusive (`>=`, a change in the second of the client's last sync is not lost; merge by ulid). |
| `GET /conversations/queue` | Queued chats the caller can accept (their open offers, offline tickets of their categories; everything for an admin), oldest first, at most 200. |
| `GET /conversations/{ulid}` · `GET .../messages?after_seq=&limit=` | `ConversationStaff`; messages with the sender's staff id. |
| `POST /conversations/{ulid}/claim` | The atomic accept, `200 ConversationStaff`. `409 already_claimed` (`error.details.by` = the winner's name; for an agent who was offered the chat; accepting a chat that is already **yours**, a second tab or a double click, is `200` with the conversation: no event, no second "joined" line, even at capacity), `409 conversation_not_queued` (gone: cancelled, missed, closed), `409 at_capacity` (live chats >= `max_concurrent_chats`; offline tickets take no slot), `403` (not an active agent, no open offer, does not serve the category; admins who take chats may claim any queued chat). |
| `POST .../messages` · `POST .../attachments` | Same shapes as the visitor's. Only the assigned agent or an admin; the chat must be `active` (`409 conversation_not_active`). A reply on an **offline ticket** is also e-mailed (queued `OfflineTicketReply`) to the visitor's address. |
| `POST .../receipts` · `POST .../typing` | Only the assigned agent (an admin looking in does not mark a chat read). `204`; receipts are published as `message.delivered` / `message.seen` (same rules as the visitor's), typing as the realtime `typing` event. |
| `POST .../end` | Assigned agent or admin; `ended` (`ended_by` agent or admin) and the rating prompt. `409 conversation_not_active` for anything but an active live chat. A widget whose `features.rating` is off sends no rating prompt: the chat goes `active -> closed` (reason `skipped`) at once, after the `ended` event. |
| `POST .../close` | An agent resolves their claimed **offline** ticket; an admin closes any unfinished conversation (queued, active, ended): `closed`, reason `system`, no rating prompt. `409 conversation_not_open`. |
| `POST .../transfer` | `{ agent_id }` or `{ category }` (ulid or slug) on an active chat: it returns to `queued` with the assignee cleared and the history kept in `conversation_events`. A category goes through the routing waves (the agent who let go is not offered it again); an agent (active, `is_agent`, serves the chat's category) is the only one offered it and accepts it like any offer (its routing counts as complete: no wave widens it). `422` for a bad target, `409 conversation_not_active`. A **live** chat is only handed to somebody who can take it now, else `409 no_agents` and the agent keeps the chat: `details.target = agent` with `details.reason = offline` (presence offline or no heartbeat for 90 s) or `at_capacity`, or `details.target = category` with `details.reason = no_reachable_agent` (nobody who serves it, is `online`/`away` per the widget's routing waves and has a free slot, not counting the agent who lets go and the caller). Offline tickets are not checked. |
| `GET /conversations/{ulid}/transfer-targets` | Anyone who may see the conversation (`ConversationAccess::view`); only for an active **live** chat (`409 conversation_not_live` for an offline ticket, `409 conversation_not_active`). `{ data: { agents: [{ id, name, avatarUrl, status: online\|away\|offline, activeChats, maxConcurrentChats, reachable }], categories: [{ slug, label }] } }` (`TransferTargetsData`). `agents` = active agents who serve the chat's category, not the caller, not the agent who has it, with their effective presence and load; `reachable` is exactly what `POST .../transfer` accepts for that colleague. `categories` = active categories of the chat's widget, other than its own, that currently have a reachable agent (same rule as the transfer). No e-mail addresses. |
| `GET /conversations/export?format=csv\|json` | **Admin only**, same filters (and the same `q` search as the list), streamed in chunks of 500 (flat memory; PHP's time limit is lifted for the stream), `Content-Disposition: attachment`; CSV cells that start with `=`, `+`, `-`, `@` are prefixed with a quote; recorded in the audit log (`conversations.exported`). |
| `GET /me/presence` · `PUT /me/presence {status: online\|away\|offline}` · `POST /me/presence/heartbeat` | Any staff member. `GET` / `PUT` return `{ userId, status, isManual, lastSeenAt }` with the **effective** status. Clients beat every 30 s. |

**Presence and routing.** An agent is reachable when the account is active and `is_agent`, the stored status is `online` or `away` with a heartbeat younger than **90 s**, they serve the category and have fewer active live chats than `max_concurrent_chats`. The same rule feeds `availability.online` (and each category's `online`) of the public availability endpoint, which also needs the widget to be open and counts only the statuses the widget's routing waves can offer a chat to (the very set `POST /public/conversations` checks, so `online` never promises a chat that is then refused with `no_agents`); the cached answer is dropped when an agent starts or stops being reachable. Routing waves come from the widget's `routing.waves` (default: `online` agents at once, `away` agents after `chat.offer_wave_delay_seconds` = 20 s); each wave offers the chat to every reachable agent of the statuses so far who has no offer yet. `queue_expires_at = queued_at + widget.queue_timeout_seconds` (default 90 s), after which the chat is `missed`. Later waves are delayed jobs (`OfferNextWave`, 3 tries); the per-minute `chat:offer-waves` sweep makes any wave that is due but never ran (a failed job, or the `sync` queue driver, which runs a delayed job at once and so too early). A job carries the chat's `claim_version`, its queue epoch, and is ignored after a transfer.

### Rate limits (per minute, `config/chat.php` `rate_limits`)

| Limiter | Applies to | Default |
|---|---|---|
| `public-session` | session creation: per client network / per network + widget key | 60 / 30 |
| `public-message` | visitor calls: per session 240 (reads, receipts, typing, end, rating, ...), **30 for message sends**, per client network 600; **chat starts** (`POST /public/conversations`) also per widget + network and per widget overall (`start_per_widget_network` / `start_per_widget`); signed attachment downloads count against the network | 3 / 120 for starts |
| `public-upload` | image uploads per session (and the network ceiling) | 10 |
| `public-offline` | offline tickets per session / per client network; plus per widget + network and per widget overall (`offline_per_widget_network` / `offline_per_widget`) | 3 / 10; 3 / 120 |
| `public-network` | **every** visitor call per client network, counted before the token is looked up (random tokens each cost a read) | 600 (`public_visitor_ip`) |
| `staff-api` | management chat calls per staff member | 600 |

`429 rate_limited` carries `Retry-After`.

**Chat start guards** (not per-minute limiters; `ChatStartGuard`, config `chat.cancel_cooldown_seconds` = 10 and `chat.max_queued_per_network` = 3). Starting a chat fans an offer out to every reachable agent, and the Origin check does not stop a non-browser client, so: after a visitor cancels a queued chat they cannot start another for 10 s (kept per visitor, so rotating the token does not skip it); at most 3 live chats wait for an agent at once from one client network on one widget (counted through `visitor_sessions.network_hash`, a keyed hash of the network, never the address). Both answer `429 rate_limited` with `Retry-After` and `details.retry_after`. The defaults are tight for a big shared NAT: raise `start_per_widget_network` / `max_queued_per_network` there. A captcha / proof-of-work hook in front of session and chat creation is planned for P7 and is not part of this round.

### Scheduled timers (`routes/console.php`; needs `schedule:run` every minute and a queue worker)

| Command | Schedule | Effect |
|---|---|---|
| `chat:expire-queued` | every minute | Queued live chats past `queue_expires_at` become `missed` (a delayed `ExpireQueuedConversation` job does the same per chat; this is the safety net). Offers are expired. |
| `chat:offer-waves` | every minute | Queued live chats whose next routing wave is due (`queued_at` + the wave's delay) but was never made get it now; idempotent (an agent who has an offer is never offered again), waves are cumulative so the last due one runs. Needed with the `sync` queue driver and as a net under lost or failed `OfferNextWave` jobs. |
| `chat:close-idle` | every minute | Active chats past `idle_expires_at` (messages move it; typing and presence do not) become `closed` (`idle`), no rating prompt, chunks of 500. Offline tickets never idle. |
| `chat:close-unrated` | every minute | `ended` chats past `rating_window_expires_at` (`chat.rating_window_minutes`, default 10) become `closed` (`timeout`). |
| `chat:prune-visitor-sessions` | daily 03:45 | Deletes sessions expired or revoked more than 7 days ago (their chats stay), anonymous visitors left with neither a session nor a chat, and uploads no message referenced for 24 hours (`--session-days`, `--attachment-hours`). |

Each sweep is a guarded `UPDATE ... WHERE status = :from AND <deadline>`, so a missed minute only delays a transition and two schedulers cannot move a chat twice.

| `GET /me/notification-settings` | `{ sound, pushOffers, pushMessages, includePreview, quietHours: { enabled, start, end, timezone }, promptState: never\|granted\|denied\|snoozed, promptedAt, snoozedUntil, previewsAllowed, pushAvailable, snoozeDays }`. A member who never saved anything gets the defaults (all on, quiet hours off `22:00`-`07:00` in their own timezone, `never`) and no row is created. `previewsAllowed` is the administrator's setting `notifications.push_include_preview`; `pushAvailable` is false when the VAPID keys are not configured. |
| `PUT /me/notification-settings` | Any subset of `sound`, `push_offers`, `push_messages`, `include_preview` (booleans), `quiet_hours { enabled, start, end, timezone }` (merged field by field; `HH:MM`; a known IANA zone; with the window on, `start` and `end` must differ: `422` on `quiet_hours.end`) and `prompt_state` (`never\|granted\|denied\|snoozed`). `snoozed` ("Not now" on the first-login dialog) sets `snoozedUntil` to now + `push.snooze_days` (7), computed by the server; any state but `never` stamps `promptedAt`. Answers the whole settings object. |
| `GET /me/push-subscriptions` | `{ data: PushSubscription[], meta: { next_cursor: null } }`, newest first: `{ id (ulid), label ("Chrome on macOS"), userAgent, host (the push service), endpointHash (sha-256 of the endpoint: a browser recognises its own row by hashing its endpoint), createdAt, lastUsedAt, expiresAt }`. **The endpoint and the keys are never returned.** |
| `POST /me/push-subscriptions` | The browser's `PushSubscription.toJSON()`: `{ endpoint, expirationTime, keys: { p256dh, auth } }` (+ optional `content_encoding`). An **upsert by the hash of the endpoint**: `201` for a new browser, `200` when it was known (keys refreshed). A browser another member of staff signs in to is **handed over** to the caller (the device belongs to whoever uses it). The endpoint must be an `https` URL of a **public** host (`OutboundUrlGuard`: loopback, private, link-local and metadata addresses are `422`, because the server posts to it); keys must decode to a 65-byte P-256 point and a 16-byte secret. The web session that registered it is remembered (sha-256) so signing out removes the subscription. At most `push.max_subscriptions_per_user` (10): the least recently used go first. `503 push_unavailable` without VAPID keys. Limiter `push-subscriptions` (20 a minute and user). |
| `DELETE /me/push-subscriptions/{id}` | `204`; `404 subscription_not_found` for anything that is not the caller's. |
| `POST /me/push-subscriptions/test` | A **real** push to the caller's own browsers, sent right away (5 s timeout per device): `{ devices, sent, failed, removed }` (`removed` = subscriptions the push service said are gone: deleted). `409 no_push_devices` without a registered browser, `503 push_unavailable`. Limiter `push-test` (3 a minute and user). |
| `POST /me/devices` · `DELETE /me/devices/{id}` | The FCM stub for the future mobile app: `{ platform: android\|ios, token }` stored encrypted (upsert by the token's hash; a token another member registered moves to the caller), `{ id, platform, lastSeenAt }` back, never the token; `404 device_not_found`. Nothing is sent to a device yet (`push.fcm.enabled` is off). |

Page route: `GET /settings/notifications` (Inertia `settings/notifications`). `GET /manifest.webmanifest` is the generated web app manifest (no session, no cookie, `Cache-Control: public, max-age=300`). The shared Inertia prop `push: { vapidPublicKey } | null` is `null` for guests, for accounts without chat access and whenever the VAPID keys are missing.

New codes: `push_unavailable` (503), `no_push_devices` (409), `subscription_not_found` / `device_not_found` (404).
