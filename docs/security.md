# Security

> Status: written after P3. It lists the threats the design answers and the controls that are **implemented and tested through P3**, then what is still open. Chat, visitor-session, upload, realtime and WhatsApp controls arrive with P4-P6; the full sweep is P7. Nothing here replaces a pen test. Rules for contributors: [CLAUDE.md](../CLAUDE.md) "Security rules".

## Threat model in one page

| Asset | Who may want it | Main attack surfaces today |
|---|---|---|
| Staff accounts and sessions | Anyone on the internet | Login form (password spray), setup wizard before install, stolen cookie/token, an upstream (portal) outage or takeover |
| Auth-portal service token and NATS token | A malicious or compromised admin; a server-side request forger | Settings > Auth / wizard (admin-typed addresses), logs, flashed form input, audit rows |
| Widget identity secret (HS256) | Anyone who wants to impersonate a logged-in visitor | The Embed tab, rotation response, forged or replayed JWTs |
| The widget itself (what runs on customers' sites) | Hostile scripts on a host page; unlisted sites embedding or calling the widget | `/w/{key}.js`, the public config API, the iframe, `postMessage`, `window.__PNE_CHAT_BOOT__` |
| Dashboard data (widgets, agents, categories) | A lower-privileged staff member | Management API, Inertia pages (agent vs admin) |
| Availability of the app | Scanners and floods | Public widget endpoints, login, wizard |

Trust boundaries: the visitor's browser and the host page are **untrusted** (any script on the host page can read what the loader exposes); the host website's backend is trusted only for what it signs; the pizzasys portal and NATS are **external** (their answers are verified, their addresses are admin-typed and therefore guarded); the admin is trusted but typos and stolen sessions are assumed.

## Controls implemented through P3

**Install gate and setup token.** Until `storage/app/installed.lock` exists every web request goes to `/setup` and API calls get `503 not_installed`; afterwards `/setup/*` is a 404 forever. The wizard needs the one-time `SETUP_TOKEN` (constant-time comparison of hashes, remembered per browser session, 5 attempts a minute per IP, never rendered into a response, log or the state file). It is skipped **only** for `APP_ENV=local` requests whose TCP peer is loopback and that carry no proxy header; a deployment that forgot `APP_ENV=production` still asks, and without a configured token the wizard refuses to run (fail closed). The wizard cannot take over an existing account; the lock and state files are created `0600`; the state file keeps portal tokens encrypted and no password.

**Authentication and authorisation.** Mode 1: Fortify (2FA, passkeys, password confirmation for security settings; production password rules: 12+ characters, mixed case, digits, symbols, not compromised). Mode 2: sign-in is server side (the browser never talks to the portal), the portal token never leaves the server. The application reads only `users.is_admin` / `users.is_agent`; one `Gate::before` for active admins; route aliases `session.valid`, `chat.access`, `admin`; agents get `403` on every admin endpoint and page. Login is throttled per email + address, per address and per email. Staff API tokens carry the ability `staff`, expire after `SANCTUM_EXPIRATION_MINUTES` (30 days) and are deleted when the account is deactivated or loses its last chat role. Dashboard calls use the Sanctum cookie with CSRF (`419 csrf_mismatch`).

**Session revocation and portal resilience (mode 2).** Every session is re-verified against the portal (cache TTL 60 s, 15 s negative cache, single-flight); `active:false` ends the session; a deactivated identity, a switched environment, a changed role mapping or lost chat access end it too. An outage never logs anybody out: grace window, then `503 auth_unavailable`. A circuit breaker (5 failures in 30 s) protects the portal and only counts outages, so a password spray cannot open it. A rejected *service* credential fails closed for new sign-ins. NATS events only speed this up; `user.deleted` deactivates the identity (recoverable), payloads are never logged and `user.updated` is never read (it leaks a hash). The scheduled `chat:auth:prune-sessions` revokes abandoned sessions because upstream tokens never expire.

**Outbound requests (SSRF guard).** Portal and NATS addresses typed by an admin go through `OutboundUrlGuard` in validation and again before each call: canonical spellings only, every resolved address must be public (loopback, private, CGNAT, link-local, cloud metadata and their IPv4-mapped/NAT64/6to4 forms are refused), `http` only for local development, one fixed refusal message, the validated address is pinned for the connection. `PORTAL_ALLOW_PRIVATE_HOSTS` (or `APP_ENV=local`) lifts only the private-network refusal. NATS verifies certificate and host name (`NATS_TLS_CA_FILE`) and never silently downgrades to plaintext. A stored token is **never reused for a new destination** (changed address, service name or NATS address, or TLS verification turned off, requires the token again; the active environment is tested before saving).

**Secrets.** Service/NATS tokens, widget identity secrets and encrypted settings are encrypted at rest with the app key; they are **write-only** (`has_*` flags only; the identity secret is shown once on rotation with `no-store`); form rejections never flash them (`dontFlash`, including the wizard's dotted keys); Inertia DevTools redact them; the audit logger redacts keys that look like secrets; connection parameters are `#[SensitiveParameter]`; the dead-letter file holds metadata only; the public `portalUrl` is only `https://<public host>`. `.env` is never committed; `INSTALL_*` are removed after the install.

**Widget origin policy, CORS and framing.** The per-widget domain whitelist (`OriginMatcher`: bare entry = https only, `http://` only by explicit prefix or for development hosts, wildcards never on public suffixes and never the apex, label-boundary matching, no userinfo/paths/`null` origins) decides CORS on the public API (unknown or disabled widget `404`, unlisted `Origin` `403` with no CORS header, no `Origin` only for widgets that allow non-browser clients) and `frame-ancestors` on `/embed/{key}` (`'none'` when empty; hosted page `'none'`). `/w/{key}.js` refuses (`403`, `Vary: Referer`, `no-store`) a page whose `Referer` origin is not on the list, so an unlisted site does not even get the bubble; a request without a `Referer` is served because the config in it is public, and the iframe and every API call stay origin-checked. The public delivery routes (`/w/{key}.js`, `/embed/{key}`, `/c/{key}`) run without the web middleware group: no session, no cookies. The admin-only preview (`?preview=1`) reads the session cookie and strips every cookie from the response.

**Identity JWT.** HS256 only (`none`/other algorithms refused before signature work), `iss` = the widget key, `exp` required and at most 5 minutes ahead, optional single-use `jti`, strict claim typing and size caps. Unsigned `setVisitor` data is marked unverified. (The endpoint that consumes the token is P4.)

**Loader and iframe.** The loader accepts a boot config only when its `appOrigin` equals the origin the script came from and its embed URL is exactly `/embed/<key>`; the panel gets a boot object rebuilt from validated fields; client overrides are whitelisted and can only restrict or restyle; host code sees only whitelisted event metadata (message text is opt-in, fixed at boot); `postMessage` is checked for origin **and** source and never sent to `'*'`; the iframe is sandboxed; the stored visitor session is bound to the identity it was created for and deleted on sight when stale. The panel's own checks arrive with P4.

**Rate limits.** Public widget endpoints: per client network across keys (IPv6 by /64), per unknown key lookups, per widget and network, per widget and allowed origin; only requests of allowed origins use a widget's budget; `429` stays readable by allowed origins. Login: three counters. Wizard and Settings > Auth endpoints have their own named limiters.

**Headers and errors.** Dashboard and auth pages send `X-Frame-Options: SAMEORIGIN` + `frame-ancestors 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`; embed pages and the loader send their own. Every `api/*` error uses one envelope and production 500s carry no details. Behind Caddy `TRUSTED_PROXIES` makes client IP/scheme correct for the limiters and the audit log.

**Audit and identifiers.** Security-relevant writes (settings, auth environments incl. address changes, roles, widgets, agents, secret rotation, environment switches) are recorded with actor, IP and user agent. Only ULIDs and `wk_` keys leave the server; integer ids appear only in staff-only payloads.

## Controls added for the live chat (P4, after the independent reviews)

**Visitor tokens.** `vt_` + 40 random characters, only the sha256 stored. A rotation (a returning token starts a session again) caps the previous token to 60 seconds more life, in the same transaction, and never extends it: a stale or stolen token dies with the window and cannot rebind an open chat. `DELETE /public/sessions` revokes every active session of the visitor. Every `{ulid}` is checked against the session (another visitor's conversation is `404`).

**Anti-automation of the public API.** The Origin check can be forged by a non-browser client, so floods are limited by what they cost agents: chat starts and offline tickets have per widget + network and per widget budgets, a cancel cooldown and a cap of chats queued per network (`docs/rest-api.md`, "Chat start guards"); every visitor call is throttled per network before its token is looked up. Network identity for the queued-chat cap is a keyed HMAC of the client network (`visitor_sessions.network_hash`), never the address. A captcha / proof-of-work hook is planned for P7.

**Uploads.** Judged by content (`finfo` + the header), re-encoded, only the new bytes stored (EXIF, comments, trailing data and any markup hidden in them do not survive; the raw upload is not scanned for byte patterns, which rejected legitimate photos). A GIF with more than one frame is refused before decoding (frame count read from the block structure) and the decoder runs with animation off: the multi-frame pixel bomb that exhausted memory is closed. Quotas: 5 MiB per file, 10 unreferenced uploads, 30 MiB per conversation (`attachment_quota_exceeded`). Signed attachment URLs are built on the configured app origin, never the request's `Host`, and expire after `chat.attachment_url_ttl_minutes`.

**Identities and names.** `visitors.external_id` (the host's id) is compared binary (`utf8mb4_0900_bin` / `utf8mb4_nopad_bin` on MySQL / MariaDB): `John` and `john` are two visitors, so one cannot take over the other's chat. Staff names shown to visitors or in e-mail are never an e-mail address (`User::public_label`); a visitor's name is stored and mailed as one line.

**Staff sessions and the dashboard's background requests.** The dashboard reads the management API (`api/*`: presence, queue, lists, messages) and authorises its websocket channels (`POST /broadcasting/auth`) with the session cookie all the time, and right after every page load. Those requests only READ the session (`StartSessionReadOnlyForApi`, bound over Laravel's `StartSession`): they authenticate and check CSRF from it but never save it, age flash data, store the previous URL or answer with a session or `XSRF-TOKEN` cookie (`PreventRequestForgeryWithoutCookieForApi`); every other request, the Fortify and Inertia pages included, runs the stock code. Before, each of them rewrote the whole session (file / database drivers: the last writer wins), so a request that was already running when a page request stored something overwrote it: the URL a password confirmation returns to, a flash message, the "Your session has ended" notice, and a response that arrived late re-sent an old cookie. API CSRF is unchanged (`419` for a cookie request without the token). A read-only request cannot end a session either (it could not save the result): a revoked or demoted account is answered `401 session_revoked` / `403 no_chat_access` and the page request that follows ends the session, revokes the portal session (mode 2) and carries the notice to the sign-in page; bearer-token (mobile) requests have no session and behave as before. Because API calls no longer extend the sliding session lifetime (`SESSION_LIFETIME`, 120 minutes), the staff host sends `GET /session/keepalive` (204, `no-store`, `auth` + `session.valid` + `chat.access`) every 20 minutes and when a tab that was hidden for more than 10 minutes comes back; it is an ordinary page request that saves the session, keeps pending flash data and never becomes the "previous URL". A lifetime below about 30 minutes would still expire an inbox that is open and idle.

**Known limits.** Visitor websockets that were subscribed before a token was revoked stay subscribed until they disconnect ([realtime.md](realtime.md), "Known limits"); the proof-of-work / captcha hook is not built; the network cap and the start budgets can be tight behind a large shared NAT (they are config, not code).

## Still open (do not assume these are covered)

- **P5-P6 surfaces** do not exist yet: WhatsApp webhook signatures and agent isolation, push notifications. Each needs its own tests when it lands. (The P4 chat surfaces exist and are described above.)
- **P7 sweep:** a full CSP for the dashboard (only framing is restricted today; no script/style nonces), HSTS and further headers at Caddy, WAF/rate limiting in front of the public widget endpoints, `composer audit` / `npm audit` and dependency pinning review, EXPLAIN review, upload fuzzing, k6 load test (about 1k sockets).
- **Known limits of what exists:** the built-in public-suffix list that rejects `*.co.uk`-style wildcards is partial; the SSRF guard has a DNS-rebinding window of a few milliseconds when PHP's stream handler is used instead of curl; NATS "TLS first" servers are unsupported and a real NATS server has never been run against the consumer; `/embed/{key}` is cached publicly for 60 s, so a domain change reaches `frame-ancestors` within about a minute; the visitor session token sits in host `localStorage` and is readable by every script on the host page (accepted, scoped to one visitor, expiring); the loader's clamps for client overrides are looser than the dashboard's; the portal-side weaknesses recorded in [pizzasys-findings.md](pizzasys-findings.md) (no login throttling, account enumeration, CORS `*`, no service-token overlap) are outside this app.
- **Process:** in P1 the `/security-review` and `/simplify` skills could not run because they shell out to the blocked system git (see [changelog.md](changelog.md)); a manual pass stood in. Make sure they run at every later gate, the P7 sweep included.
