# Security

> Status: written after P3. It lists the threats the design answers and the controls that are **implemented and tested through P3**, then what is still open. Chat, visitor-session, upload, realtime and WhatsApp controls arrive with P4-P6; the full sweep is P7. Nothing here replaces a pen test. Rules for contributors: [CLAUDE.md](../CLAUDE.md) "Security rules".

## Threat model in one page

| Asset | Who may want it | Main attack surfaces today |
|---|---|---|
| Staff accounts and sessions | Anyone on the internet | Login form (password spray), setup wizard before install, stolen cookie/token, an upstream (portal) outage or takeover |
| Auth-portal service token and NATS token | A malicious or compromised admin; a server-side request forger | Settings > Auth / wizard (admin-typed addresses), logs, flashed form input, audit rows |
| Widget identity secret (HS256) | Anyone who wants to impersonate a logged-in visitor | The Embed tab, rotation response, forged or replayed JWTs |
| The widget itself (what runs on customers' sites) | Hostile scripts on a host page; unlisted sites embedding or calling the widget | `/w/{key}.js`, the public config API, the iframe, `postMessage`, `window.__PNE_CHAT_BOOT__` |
| Dashboard data (widgets, agents, categories) | A lower-privileged staff member | Management API, Inertia pages (agent vs admin) |
| Availability of the app | Scanners and floods | Public widget endpoints, login, wizard |

Trust boundaries: the visitor's browser and the host page are **untrusted** (any script on the host page can read what the loader exposes); the host website's backend is trusted only for what it signs; the pizzasys portal and NATS are **external** (their answers are verified, their addresses are admin-typed and therefore guarded); the admin is trusted but typos and stolen sessions are assumed.

## Controls implemented through P3

**Install gate and setup token.** Until `storage/app/installed.lock` exists every web request goes to `/setup` and API calls get `503 not_installed`; afterwards `/setup/*` is a 404 forever. The wizard needs the one-time `SETUP_TOKEN` (constant-time comparison of hashes, remembered per browser session, 5 attempts a minute per IP, never rendered into a response, log or the state file). It is skipped **only** for `APP_ENV=local` requests whose TCP peer is loopback and that carry no proxy header; a deployment that forgot `APP_ENV=production` still asks, and without a configured token the wizard refuses to run (fail closed). The wizard cannot take over an existing account; the lock and state files are created `0600`; the state file keeps portal tokens encrypted and no password.

**Authentication and authorisation.** Mode 1: Fortify (2FA, passkeys, password confirmation for security settings; production password rules: 12+ characters, mixed case, digits, symbols, not compromised). Mode 2: sign-in is server side (the browser never talks to the portal), the portal token never leaves the server. The application reads only `users.is_admin` / `users.is_agent`; one `Gate::before` for active admins; route aliases `session.valid`, `chat.access`, `admin`; agents get `403` on every admin endpoint and page. Login is throttled per email + address, per address and per email. Staff API tokens carry the ability `staff`, expire after `SANCTUM_EXPIRATION_MINUTES` (30 days) and are deleted when the account is deactivated or loses its last chat role. Dashboard calls use the Sanctum cookie with CSRF (`419 csrf_mismatch`).

**Session revocation and portal resilience (mode 2).** Every session is re-verified against the portal (cache TTL 60 s, 15 s negative cache, single-flight); `active:false` ends the session; a deactivated identity, a switched environment, a changed role mapping or lost chat access end it too. An outage never logs anybody out: grace window, then `503 auth_unavailable`. A circuit breaker (5 failures in 30 s) protects the portal and only counts outages, so a password spray cannot open it. A rejected *service* credential fails closed for new sign-ins. NATS events only speed this up; `user.deleted` deactivates the identity (recoverable), payloads are never logged and `user.updated` is never read (it leaks a hash). The scheduled `chat:auth:prune-sessions` revokes abandoned sessions because upstream tokens never expire.

**Outbound requests (SSRF guard).** Portal and NATS addresses typed by an admin go through `OutboundUrlGuard` in validation and again before each call: canonical spellings only, every resolved address must be public (loopback, private, CGNAT, link-local, cloud metadata and their IPv4-mapped/NAT64/6to4 forms are refused), `http` only for local development, one fixed refusal message, the validated address is pinned for the connection. `PORTAL_ALLOW_PRIVATE_HOSTS` (or `APP_ENV=local`) lifts only the private-network refusal. NATS verifies certificate and host name (`NATS_TLS_CA_FILE`) and never silently downgrades to plaintext. A stored token is **never reused for a new destination** (changed address, service name or NATS address, or TLS verification turned off, requires the token again; the active environment is tested before saving).

**Secrets.** Service/NATS tokens, widget identity secrets and encrypted settings are encrypted at rest with the app key; they are **write-only** (`has_*` flags only; the identity secret is shown once on rotation with `no-store`); form rejections never flash them (`dontFlash`, including the wizard's dotted keys); Inertia DevTools redact them; the audit logger redacts keys that look like secrets; connection parameters are `#[SensitiveParameter]`; the dead-letter file holds metadata only; the public `portalUrl` is only `https://<public host>`. `.env` is never committed; `INSTALL_*` are removed after the install.

**Widget origin policy, CORS and framing.** The per-widget domain whitelist (`OriginMatcher`: bare entry = https only, `http://` only by explicit prefix or for development hosts, wildcards never on public suffixes and never the apex, label-boundary matching, no userinfo/paths/`null` origins) decides CORS on the public API (unknown or disabled widget `404`, unlisted `Origin` `403` with no CORS header, no `Origin` only for widgets that allow non-browser clients) and `frame-ancestors` on `/embed/{key}` (`'none'` when empty; hosted page `'none'`). `/w/{key}.js` refuses (`403`, `Vary: Referer`, `no-store`) a page whose `Referer` origin is not on the list, so an unlisted site does not even get the bubble; a request without a `Referer` is served because the config in it is public, and the iframe and every API call stay origin-checked. The public delivery routes (`/w/{key}.js`, `/embed/{key}`, `/c/{key}`) run without the web middleware group: no session, no cookies. The admin-only preview (`?preview=1`) reads the session cookie and strips every cookie from the response.

**Identity JWT.** HS256 only (`none`/other algorithms refused before signature work), `iss` = the widget key, `exp` required and at most 5 minutes ahead, optional single-use `jti`, strict claim typing and size caps. Unsigned `setVisitor` data is marked unverified. (The endpoint that consumes the token is P4.)

**Loader and iframe.** The loader accepts a boot config only when its `appOrigin` equals the origin the script came from and its embed URL is exactly `/embed/<key>`; the panel gets a boot object rebuilt from validated fields; client overrides are whitelisted and can only restrict or restyle; host code sees only whitelisted event metadata (message text is opt-in, fixed at boot); `postMessage` is checked for origin **and** source and never sent to `'*'`; the iframe is sandboxed; the stored visitor session is bound to the identity it was created for and deleted on sight when stale. The panel's own checks arrive with P4.

**Rate limits.** Public widget endpoints: per client network across keys (IPv6 by /64), per unknown key lookups, per widget and network, per widget and allowed origin; only requests of allowed origins use a widget's budget; `429` stays readable by allowed origins. Login: three counters. Wizard and Settings > Auth endpoints have their own named limiters.

**Headers and errors.** Dashboard and auth pages send `X-Frame-Options: SAMEORIGIN` + `frame-ancestors 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`; embed pages and the loader send their own. Every `api/*` error uses one envelope and production 500s carry no details. Behind Caddy `TRUSTED_PROXIES` makes client IP/scheme correct for the limiters and the audit log.

**Audit and identifiers.** Security-relevant writes (settings, auth environments incl. address changes, roles, widgets, agents, secret rotation, environment switches) are recorded with actor, IP and user agent. Only ULIDs and `wk_` keys leave the server; integer ids appear only in staff-only payloads.

## Controls added for the live chat (P4, after the independent reviews)

**Visitor tokens.** `vt_` + 40 random characters, only the sha256 stored. A rotation (a returning token starts a session again) caps the previous token to 60 seconds more life, in the same transaction, and never extends it: a stale or stolen token dies with the window and cannot rebind an open chat. `DELETE /public/sessions` revokes every active session of the visitor. Every `{ulid}` is checked against the session (another visitor's conversation is `404`).

**Anti-automation of the public API.** The Origin check can be forged by a non-browser client, so floods are limited by what they cost agents: chat starts and offline tickets have per widget + network and per widget budgets, a cancel cooldown and a cap of chats queued per network (`docs/rest-api.md`, "Chat start guards"); every visitor call is throttled per network before its token is looked up. Network identity for the queued-chat cap is a keyed HMAC of the client network (`visitor_sessions.network_hash`), never the address. A captcha / proof-of-work hook is planned for P7.

**Uploads.** Judged by content (`finfo` + the header), re-encoded, only the new bytes stored (EXIF, comments, trailing data and any markup hidden in them do not survive; the raw upload is not scanned for byte patterns, which rejected legitimate photos). A GIF with more than one frame is refused before decoding (frame count read from the block structure) and the decoder runs with animation off: the multi-frame pixel bomb that exhausted memory is closed. Quotas: 5 MiB per file, 10 unreferenced uploads, 30 MiB per conversation (`attachment_quota_exceeded`). Signed attachment URLs are built on the configured app origin, never the request's `Host`, and expire after `chat.attachment_url_ttl_minutes`.

**Identities and names.** `visitors.external_id` (the host's id) is compared binary (`utf8mb4_0900_bin` / `utf8mb4_nopad_bin` on MySQL / MariaDB): `John` and `john` are two visitors, so one cannot take over the other's chat. Staff names shown to visitors or in e-mail are never an e-mail address (`User::public_label`); a visitor's name is stored and mailed as one line.

**Staff sessions and the dashboard's background requests.** The dashboard reads the management API (`api/*`: presence, queue, lists, messages) and authorises its websocket channels (`POST /broadcasting/auth`) with the session cookie all the time, and right after every page load. Those requests only READ the session (`StartSessionReadOnlyForApi`, bound over Laravel's `StartSession`): they authenticate and check CSRF from it but never save it, age flash data, store the previous URL or answer with a session or `XSRF-TOKEN` cookie (`PreventRequestForgeryWithoutCookieForApi`); every other request, the Fortify and Inertia pages included, runs the stock code. Before, each of them rewrote the whole session (file / database drivers: the last writer wins), so a request that was already running when a page request stored something overwrote it: the URL a password confirmation returns to, a flash message, the "Your session has ended" notice, and a response that arrived late re-sent an old cookie. API CSRF is unchanged (`419` for a cookie request without the token). A read-only request cannot end a session either (it could not save the result): a revoked or demoted account is answered `401 session_revoked` / `403 no_chat_access` and the page request that follows ends the session, revokes the portal session (mode 2) and carries the notice to the sign-in page; bearer-token (mobile) requests have no session and behave as before. Because API calls no longer extend the sliding session lifetime (`SESSION_LIFETIME`, 120 minutes), the staff host sends `GET /session/keepalive` (204, `no-store`, `auth` + `session.valid` + `chat.access`) every 20 minutes and when a tab that was hidden for more than 10 minutes comes back; it is an ordinary page request that saves the session, keeps pending flash data and never becomes the "previous URL". A lifetime below about 30 minutes would still expire an inbox that is open and idle.

**Known limits.** The proof-of-work / captcha hook is not built; the network cap and the start budgets can be tight behind a large shared NAT (they are config, not code).

## Stale websockets are closed (P7)

Channel authorisation happens at subscribe time, so before P7 a socket that was open when a right ended kept receiving (a deactivated or demoted staff member on `private-admin` / `private-whatsapp-admin` / `private-conversation.{ulid}`, an agent a chat was transferred away from, a visitor whose token was revoked or rotated). Now every private subscription is signed with the principal's tag (`channel_data`) and the server asks Reverb to terminate the sockets that carry it when the right ends: an account losing `is_active` / `is_admin` / `is_agent` or being deleted, a mode 2 session revocation, a sign-out, a conversation transferred / assigned / claimed by somebody else (for the agents that hold a recorded grant and no longer pass `ConversationPolicy::viewAsStaff()`), a visitor token revoked, rotated or expired. The tag is an HMAC under `APP_KEY` (whispers are re-broadcast with it, so it must not be an id); a call that fails is parked and retried, every cut is repeated after 20 s, and `chat:realtime-sweep` (scheduler, every minute) covers token expiry and lost events. Design, triggers, limits and the real-socket proof: [realtime.md](realtime.md) "Cutting a socket off". Residual: a pre-signed `pusher:subscribe` held back by an insider until after the cut (the signature has no expiry); `php artisan reverb:restart` is the hard cut-off.

## Controls added for web push (P5, hardened in the fix round)

**Push endpoints (SSRF).** A browser hands the server the URL of its push service and the server later POSTs to it, so an endpoint is a request-forgery target that a signed-in member of staff chooses. `PushEndpointGuard` is stricter than the guard for addresses an administrator types in: https only, printable ASCII without a backslash, no credentials or fragment, no trailing-dot host, **port 443 only** (a port is allowed only when an entry of `push.allowed_hosts` names it), and the host must be **public in every answer**: loopback, private, CGNAT, link-local, cloud-metadata addresses, every odd spelling of them (`0x7f.1`, `2130706433`, `0177.0.0.1`, `localhost`, `[::ffff:127.0.0.1]`) and any name that resolves to one of them are refused **whatever `PORTAL_ALLOW_PRIVATE_HOSTS` and `APP_ENV` say** (that switch is for the OpenWA gateway and the auth portal, never for a browser's URL). `push.allowed_hosts` (env `PUSH_ALLOWED_HOSTS`, comma separated; `*.example.com` = any sub-domain, never the bare domain) narrows it to the vendors' hosts (`fcm.googleapis.com`, `*.push.services.mozilla.com`, `web.push.apple.com`, `*.notify.windows.com`); empty means any public host. The judgement of a host (its resolved addresses) is cached for 60 s, the **connection is pinned to it** (`CURLOPT_RESOLVE`, so DNS is resolved once per host and minute and a name re-pointed at the internal network after the judgement cannot steer the request there), redirects are never followed and the per-request timeout really reaches the HTTP client. The test seam is the container-bound `HostResolver` fake of the test suite, never an environment switch.

**Push DoS.** "Send a test notification" is synchronous, so it is bounded: at most 5 devices (the most recently used first), 5 s per device and **10 s for all of them together**; queued pushes keep 10 s per device but one job has a 60 s budget across a member's devices (the rest is retried). Registration is limited to 20 a minute and member and 10 browsers each.

**Offers that closed.** A push is queued first and runs later: the job asks again whether the offer is still open (a chat taken, cancelled or expired before the job ran is never rung for) and dismisses at once an offer that closes while it is being sent; the "who was pushed" marker is written before the job is queued, so a dismiss that follows immediately finds it.

**Service worker.** `pushsubscriptionchange` re-registers with the URL-decoded `XSRF-TOKEN` (the cookie is percent-encoded; the header carries the decoded token, as the API client sends it).

## Controls added for WhatsApp (P6)

Design: [contracts/whatsapp-p6.md](contracts/whatsapp-p6.md); operations: [whatsapp-openwa.md](whatsapp-openwa.md), [runbook.md](runbook.md); the tests that pin every line below are `tests/Feature/WhatsApp/*` (the isolation matrix alone is 217 cases).

**Isolation (P6-D1).** WhatsApp is **administrators only, in three places**: the `wa.admin` middleware (policy `viewAny`) on every route and page, `WhatsAppPolicy` asked again inside every action (so an action called from anywhere refuses an agent by itself; `Gate::before` lets an admin through every ability, so the rules that depend on state are in the actions, not in the policy), and the channel `private-whatsapp-admin`. An agent, an account without a chat role, a deactivated administrator, a visitor token and a guest get `403` / `401` on every route (a matrix test walks every registered route containing `whatsapp` and fails on one that is missing from it or lacks `wa.admin`), a refused call changes nothing, calls OpenWA never and queues nothing, and the refusal says nothing about WhatsApp. WhatsApp chats are in no conversation list, search, staff export, Inertia prop or broadcast an agent can reach; the staff conversation search and export never join `wa_*`.

**The webhook (`POST /webhooks/openwa/{session}`).** The only credential is the HMAC-SHA256 of the **raw body** with the session's own secret, checked before anything is read, stored or queued: constant time, always the same work (a missing or malformed header, an uppercase hex, a session without a secret and a wrong secret all compute the same HMAC and answer the same generic `401`), other sessions' secrets do not open it, a body over 1 MiB is `413` before the HMAC, an unknown or deleted session `404`. The recorded real deliveries of OpenWA 0.23.7 verify against it. The body, the header and the secret are never logged. **Only the signed body is trusted**: the event name (a body without a usable one is `400`), the delivery id and the dedupe key come from the body (`idempotencyKey`, or a hash of the body when it has none), never from the `X-OpenWA-*` headers, which the signature does not cover: a captured delivery replayed with a fresh header key is still the same delivery, a `200` no-op (`X-OpenWA-Delivery-Id` is never a dedupe key). The unique `(chat, message id)` index is the real guard (a re-registered webhook changes every key), a delivery names the OpenWA session it belongs to (another session's event is ignored), session events older than the newest applied are ignored (the newest applied moment is kept in the database, `whatsapp_sessions.last_event_ms`, so it survives a cache flush and a pruned ledger row), acks are forward-only, and a failing delivery is retried a few times and then recorded as `failed` with a one-line error that never contains SQL or message text (`SafeError`). A limiter keyed per session AND client network (3000 a minute) with a ceiling per client network (6000) bounds a flood without letting one session starve another or a stranger use up OpenWA's own budget. A queue that cannot take the job removes the ledger row again, so a delivery is never "seen" with nobody owning it, and an accepted delivery is **durable**: its raw body stays on the ledger row until it is processed, so a job the queue lost or a delivery that ran out of tries is queued again by `whatsapp:replay-deliveries` (every 5 minutes, at most 5 replays each); a retried delivery of a message that was stored but not finished (the queue refused the media job, the linker was a deadlock victim) completes its media, link and events instead of being taken for a finished duplicate.

**Secrets.** The OpenWA API key is encrypted at rest, write-only (`hasApiKey` only), never returned, logged, audited or flashed (an exception message is a fixed sentence; the key travels only in the `X-API-Key` header and is hidden from dumps), and a changed OpenWA address needs the key typed again in the same request. The per-session webhook secret is generated by the application (40 random characters), stored encrypted, never returned and never in the URL; a replacement is a deliberate action (`POST .../webhook`) and a secret that can no longer be decrypted is replaced on the next Start. The pairing QR is a login credential while it is valid: encrypted at rest, fetched only by an administrator over `GET .../qr` with `Cache-Control: no-store`, only while the session waits for a scan, never in a list, a prop or a broadcast, and dropped as soon as the session leaves `qr`; an image that is not a base64 PNG data URL of a sane size is refused before it is stored.

**Outbound requests (SSRF).** The saved OpenWA address goes through the settings rule and again through `OutboundUrlGuard` before every call (private / loopback / metadata addresses only with `PORTAL_ALLOW_PRIVATE_HOSTS`, plain `http` only for a private target), the connection is pinned to the address that was just judged, redirects are never followed. The address OpenWA calls back is the application's own `app.url`, never the request host. OpenWA's statuses are never mirrored (a `401` from OpenWA is `502 openwa_unauthorized`, which would otherwise end the dashboard session).

**Protecting the number.** WhatsApp bans automated accounts: replies only to customers who wrote first (`whatsapp.reply_only_to_inbound`), a minimum interval per session between two sends, a daily cap per session (an atomic `UPDATE ... WHERE count < cap`, UTC day, survives a cache flush), idempotent replies (`client_msg_id`), and **no blind retry of a write that may have been carried out** (a send that was sent but never answered, a `5xx` from a proxy in front of OpenWA, a `2xx` without a usable message id, or our own bookkeeping failing after OpenWA accepted: all stay `pending` until the `message.sent` webhook confirms them or the reconciliation fails them after 30 minutes, instead of risking a message twice; only a connection that never got through, `409` and the plain throttler `429` are retried). The replies of one chat go out in the order they were written. OpenWA's own `SEND_PACING_LIMITED` is honoured, never retried blindly.

**Hand-off and linking.** Codes are 8 characters of an alphabet without look-alikes, unique across all tickets, live for `whatsapp.handoff_ttl_minutes`; a visitor's second request returns their live ticket (no code minting), a visitor creates at most 10 a day, and the endpoint has per-visitor, per-network and per-widget limits on top of the public gates (widget key, origin, visitor token bound to that widget). Because a visitor is only a bearer token that a script gets for free, the number of **live, unconsumed codes is capped per client network and widget (30) and per widget (500)**: beyond that `429` until one is used or expires. `ChatLinker` links only a **live ticket of the same session** whose code is a whole word in one of the first five inbound messages of a not-yet-linked chat (ASCII upper-casing only, so letters of other scripts never spell a code), claims the ticket with a guarded `UPDATE` under the chat's row lock (one ticket links one chat, even under concurrency: a MySQL race test), never re-links a linked chat and never links from the phone's own messages. The public config and availability say only that WhatsApp is on; **the number is only inside the `waUrl` of a hand-off**.

**Customer content.** Messages are plain text (control and bidirectional-override characters removed, line endings normalised) and rendered as text by every client. The raw webhook object is kept for debugging only, without inline media, capped, never returned. Inbound images are judged by content and re-encoded by the chat's `ImageSanitizer` (EXIF and trailing data do not survive, size / pixel / animation limits), stored on the private disk under a random path and served only by a URL that is signed (60 minutes) **and** needs an administrator's session, with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and a neutral file name; anything else (documents, audio, video, stickers) is recorded as a typed row without a file. The export and the audit log: CSV cells that look like formulas are quoted, every export and every administrative action (sessions, settings, link, archive, replies as ids and lengths) is audited without message text or secrets.

**Retention and erasure.** The raw webhook object kept in `wa_messages.raw` is for debugging only: it is dropped after `whatsapp.raw_retention_days` (default 30; 0 stores nothing, except the chat id a large image's fetch needs), and so are the raw bodies of failed deliveries still waiting for a replay (at least a day). `whatsapp.retention_days` (default 0 = keep for ever) deletes messages, their stored images and then the emptied chats older than that many days; both run in the daily `whatsapp:prune`. An administrator erases one customer's chat on request with `DELETE /whatsapp/chats/{ulid}` (messages and images included, idempotent, audited with ids and counts only, never the number, name or text; a hand-off ticket stays, unlinked); a failed file delete leaves an orphan that the prune removes within a day. Looking at a pairing QR is audited (`whatsapp.session.qr_viewed`, once per administrator and session per five minutes, never the image).

**Known limits.** The shapes of customer messages and acks come from OpenWA's reference (a paired phone was not available to record them); the recorded parts (sessions, QR, webhook registration and signing, errors) match the real image. A signed delivery has no timestamp the application can check: a captured delivery replayed after its ledger row was pruned (30 days) is processed again (the unique message index and forward-only statuses make that harmless for messages and acks; a replayed session event is dropped by the ordering mark kept in the database). A customer can type any code they can read (a screenshot of somebody else's), which is why a ticket links once and expires. The visitor sees the connected number in the `wa.me` link by design.

## Still open (do not assume these are covered)

- **P5 surfaces** (push notifications) are described where they landed; the P6 WhatsApp surface is described above and pinned by `tests/Feature/WhatsApp`. A real-device round trip (inbound payload shapes, acks) has not been run.
- **P7 sweep:** a full CSP for the dashboard (only framing is restricted today; no script/style nonces), HSTS and further headers at Caddy, WAF/rate limiting in front of the public widget endpoints, `composer audit` / `npm audit` and dependency pinning review, EXPLAIN review, upload fuzzing, k6 load test (about 1k sockets).
- **Known limits of what exists:** the built-in public-suffix list that rejects `*.co.uk`-style wildcards is partial; the SSRF guard has a DNS-rebinding window of a few milliseconds when PHP's stream handler is used instead of curl; NATS "TLS first" servers are unsupported and a real NATS server has never been run against the consumer; `/embed/{key}` is cached publicly for 60 s, so a domain change reaches `frame-ancestors` within about a minute; the visitor session token sits in host `localStorage` and is readable by every script on the host page (accepted, scoped to one visitor, expiring); the loader's clamps for client overrides are looser than the dashboard's; the portal-side weaknesses recorded in [pizzasys-findings.md](pizzasys-findings.md) (no login throttling, account enumeration, CORS `*`, no service-token overlap) are outside this app.
- **Process:** in P1 the `/security-review` and `/simplify` skills could not run because they shell out to the blocked system git (see [changelog.md](changelog.md)); a manual pass stood in. Make sure they run at every later gate, the P7 sweep included.
