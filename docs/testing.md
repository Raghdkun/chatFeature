## Running the checks

```bash
composer test          # artisan config:clear + pint --test + phpstan + artisan test
composer lint          # pint --parallel (fix)    | composer lint:check (verify only)
composer types:check   # phpstan analyse
npm run check          # vp check (lint/format)   | npm run check:fix
npm run types:check    # tsc --noEmit
composer ci:check      # npm run check + npm run types:check + composer test
```

The kit's GitHub Actions workflow (`.github/workflows/tests.yml`) runs `composer setup` then `composer ci:check`. The Playwright suite is **not** part of `ci:check` (it needs MySQL, a built frontend and Google Chrome): run it with `npm run e2e` (see below). A CI job for it needs a MySQL service, `npm run build`, Chrome (`channel: 'chrome'`, or `npx playwright install chrome`) and a `.env` (`cp .env.example .env`; the suite brings its own `APP_KEY`).

## Vitest notes for the chat frontend (P4)

- **No network, ever.** The visitor panel's tests run against `useBackend()` (`tests/msw/server.ts`): a stateful fake of the public chat API (sessions with rotation and revocation, conversations, idempotent sends, receipts, uploads, the Pusher auth, injected failures via `backend.fail(...)`). An unmocked request fails the test. The agent inbox uses `useStaffBackend()` the same way. `tests/embed-harness.ts` wires a real `ChatController` to a recording host, a scriptable fake socket and that backend; `renderPanel()` mounts the real `App` on top of it.
- **Real Echo, fake Pusher.** `tests/echo-integration.test.tsx` (staff) and `lib/realtime/visitor/echo-integration.test.ts` (visitor) run the real `laravel-echo` with only the Pusher client replaced, because the other suites replace Echo entirely and so cannot notice a wrong event name (custom events need the leading dot), a whisper that is not sent as `client-<name>`, or a binding that survives `close()`.
- **Clocks.** Offer deadlines, the 45 s "give up on a sync pass" rule and request deadlines are tested with fake timers or an injected `now`; the deadline of an offer is counted from its arrival in the agent's browser when the server sends `ttlSeconds`, so a skewed agent clock is covered by a store test.

## End-to-end tests (Playwright)

```bash
npm run build && npm run build:widget   # the suite drives the built assets (public/build, public/widget/v1/loader.js); globalSetup rebuilds them itself when missing or older than the sources
npm run e2e                   # everything, desktop + mobile projects, headless Chrome (~4 minutes with the P3 specs)
npm run e2e:headed            # same, with a visible browser
npx playwright test e2e/auth/login.spec.ts --project=desktop      # one spec / one project
npx playwright show-report    # HTML report of the last run (traces + screenshots of failures)
npm run e2e:screenshots       # regenerate docs/screenshots/p1/*.png (see below)
```

Prerequisites: **the local pizzasys harness** (mode-2 scenarios, see below), local MySQL reachable with the credentials of `.env` (`DB_HOST/PORT/USERNAME/PASSWORD`), PHP 8.4 as `php` (override with `E2E_PHP=...`), Google Chrome installed (nothing is downloaded), `npm run build` done. The suite creates the databases it needs
(`CREATE DATABASE IF NOT EXISTS`, through the app's own connection settings) and **only ever touches databases named `chatfeature_e2e*`**; it never uses the dev database `chatfeature` or `chatfeature_testing`.

### The pizzasys harness (mode 2)

Mode-2 specs sign in through a **real pizzasys instance**: the throwaway harness that lives outside this repository (`../chatFeature.harness`, override with `E2E_HARNESS_DIR`). It serves a clone of pizzasys (SQLite, no NATS) on **127.0.0.1:8200** and is controlled with `run.sh start|stop|status|reset`. Its test accounts and service-client tokens are in `secrets.local.env` there; the suite reads that file at runtime and never copies anything from it into the repository, a spec, a report or a log. Needed once, or after the harness drifted: `../chatFeature.harness/run.sh reset` (clean baseline: users `admin@`, `chatadmin@`, `agent@`, `roleagent@`, `norole@`, `storeuser@test.local`, service clients `pne-chat` (the valid one), `other-svc`, `inactive-svc`, `expired-svc`).

`e2e/global-setup.ts` starts the harness whenever a mode-2 scenario is active (port 8200 must be free: it stops its own leftovers first and refuses to continue when something else answers), creates the suite's own portal accounts (`e2e.roles.<project>@test.local`, plain agents whose permissions the role-change spec edits) and stops the harness again in its teardown. Without the harness directory only `E2E_ONLY=...` runs of mode-1 scenarios work. **CI needs the harness** (a pizzasys clone, PHP 8.4 + SQLite) next to the checkout, or the mode-2 specs excluded: every mode-2 test carries the tag `@pizzasys`: `E2E_SKIP_PIZZASYS=1 npx playwright test --grep-invert @pizzasys` leaves out the mode-2 scenarios (no harness is started) and their tests (136 specs).

### How it works

The install wizard locks itself after the last step, so tests cannot share one server. Every **scenario** is a throwaway server of its own, declared once in `e2e/support/scenarios.ts`:

- started by Playwright's `webServer` (`php artisan serve --no-reload --host=127.0.0.1 --port=81xx`, `PHP_CLI_SERVER_WORKERS=4` so page and asset requests do not serialize) and stopped by it; nothing is left running;
- its own MySQL database, and a private storage directory `storage/e2e-<scenario>/` (`LARAVEL_STORAGE_PATH`: sessions, file cache, logs, compiled views) with the install state/lock files in `storage/e2e-<scenario>/state` (`INSTALL_STATE_DIR`). The directory is git-ignored; **`laravel.log` of a failing scenario is in there**;
- environment forced by the config (so `.env` cannot leak in): `SESSION_DRIVER=file`, `CACHE_STORE=file`, `QUEUE_CONNECTION=sync`, `BROADCAST_CONNECTION=null`, `MAIL_MAILER=log`, `BCRYPT_ROUNDS=4`, a fixed test `APP_KEY`, `APP_DEBUG=false` (`E2E_DEBUG=1` turns it on).

`e2e/global-setup.ts` resets every scenario before the suite (wipe the private storage dir, create the database, `chat:install:reset --force` env-scoped to that database) and prepares it by kind: `fresh` (nothing), `seeded` (wizard answers stored, so every wizard screen can be opened read-only with `?step=`), `installed` (`php artisan chat:install --mode=local` with `INSTALL_*` values, the extra test accounts of `e2e/support/users.ts`, and a saved admin + agent login per scenario so specs do not hit the login throttle). Playwright starts the servers *before* `globalSetup`; that is safe because readiness is checked on a static file (`/favicon.svg`), which does not boot Laravel.

### P3 scenarios: seeds, the API fixture and the cross-origin host page

- **Seeds** (`seed` in `e2e/support/scenarios.ts`, run by `e2e/global-setup.ts` right after the install): `staff` adds three categories to the installer's "General" (Billing, Sales, Technical support), the agents Sara Ibrahim (serves Billing + Sales) and Tariq Aziz (Technical support), and Khalid Mansour, an administrator who does NOT take chats (`is_agent = false`; saved login `role: 'admin-only'`). `demo` also creates the published widget "Acme Storefront" through the management API (domains, greetings, categories, branding, texts, opening hours in `Asia/Kolkata`).
- **Specs create their own data**: the stateful P3 scenarios are shared by every test of a spec file (one server per project), so each test creates the widgets / categories / agents it needs through the API under a `unique()` name and never assumes the list is otherwise empty. Retries and the second project cannot collide.
- **`api` / `adminApi` fixtures** (`e2e/support/api.ts`, `test.ts`): the management API with Sanctum's cookie + `X-XSRF-TOKEN` exactly as the dashboard's own fetch wrapper sends them. `api` shares the cookies of `page`; `adminApi` is a context of its own with the saved administrator login, for specs whose `page` plays an anonymous visitor. `createWidget()` creates, configures (domains, categories, greetings, draft + publish, settings) and enables a widget in one call.
- **The customer site** (`e2e/support/host-server.mjs`, started by Playwright's `webServer` for every instance with a `hostPort`): a tiny static server on `http://localhost:<host port>` while the app is `http://127.0.0.1:<app port>`, so every embed is genuinely cross-origin (and `APP_URL` equals the origin the loader script comes from, which the loader insists on). `GET /page.html` is driven by the query string (`hostPage()` in `e2e/support/host.ts`): `key`, `src=w|generic|none` (`/w/<key>.js`, the generic `/widget/v1/loader.js` + `data-widget-key`, or no script), `attrs` (data-* attributes), `settings` (`window.ChatFeatureSettings`), `hostile` (`* { all: unset }`, `div, button { display: none !important }`, ...), `rtl`, `csp` (a strict page CSP: script/frame/connect sources of the app only, no inline styles), `twice`, `late`, `height`, `hostname` (`localhost`, `127.0.0.1`, `a.example.localhost`: other origins, same server). Every widget event lands in `window.__events`. Wildcard whitelist entries need a base of two labels, so the specs use `*.example.localhost:<port>`; Chrome resolves every `*.localhost` name to the loopback address.
- Loader timing: greetings are configured with a 1 s delay and a 3 s auto-hide; the `interval` dismiss policy runs on `page.clock` (a minute of waiting takes no time); the 10 s handshake watchdog is waited out for real once on desktop and once on a phone viewport (written against the P3 panel stub that never sends `ready`: the real P4 panel does answer, so that spec has to provoke the timeout another way, an open item of the P4 e2e phase). Geometry is measured after `settleWidget()` (entrance animations and transitions are over).

### P4 chat scenarios: realtime, the queue, the seed and the actors

**A real Reverb per instance.** A scenario with a `reverbPort` also gets `php artisan reverb:start --host=127.0.0.1 --port=<port>` as a Playwright `webServer` (started and stopped with the app, waited for on Reverb's own `/up` route, nothing left behind) and runs with `BROADCAST_CONNECTION=reverb`, `REVERB_APP_ID/KEY/SECRET`, `REVERB_HOST=127.0.0.1`, `REVERB_PORT`, `REVERB_SCHEME=http`, `REVERB_SERVER_HOST/PORT` (public and bound address are the same here) and `REVERB_ALLOWED_ORIGINS=localhost` (the panel iframe is served by the app, so the app's host is allowed anyway). The key is the same everywhere (`e2e-reverb-key`, it is public), the secret per instance. Ports: web `8260 + n` (desktop) / `8270 + n` (mobile twin), customer site `8280 + n` / `8285 + n`, Reverb `8340 + n` / `8345 + n`; `p4-chat` is n = 0, the views n = 2 and 3; 8264-8269, 8274-8279, 8284, 8289 and 8344, 8348 are free for more P4 scenarios, **8349 is reserved** (the address baked into the dashboard build, see below; nothing listens there).

**Realtime and the queue: `QUEUE_CONNECTION=sync`, no worker, no scheduler.** Decided after reading `docs/realtime.md`, `app/Domain/Chat/Jobs/*` and the chat actions: the immediate broadcasts (`message.created`, `chat.claimed`, `session.revoked`, typing) are published by the web server process, the queued ones (`conversation.updated`, `chat.offered`, `queue.updated`, ...) run inline in the request on the sync queue, so an event is on the wire when the HTTP call that caused it returns (deterministic, no worker to start, supervise or wait for). The two delayed jobs (`OfferNextWave`, `ExpireQueuedConversation`) are written for the sync driver (they do nothing before they are due) and the per-minute sweeps are the safety net the product ships; **nothing runs them here, so time only moves when a spec moves it**: `ageConversation()` shifts the deadlines, `runSweep()` runs the sweep the scheduler would (`chat:expire-queued`, `chat:offer-waves`, `chat:close-idle`, `chat:close-unrated`). No spec waits for a timeout. (Queue timeout 45 s and a second routing wave 20 s after the chat was queued are the seeded widget's values; a spec that needs other numbers creates its own widget with `createWidget()` / `liveWidget()`.)

**The dashboard's sockets.** The staff Echo takes the Reverb address from the `realtime` shared Inertia prop at runtime (`HandleInertiaRequests` -> `ReverbEndpoint`), which is each instance's own Reverb (user ids repeat across scenarios, so a shared Reverb would mix their `staff.{id}` channels); `VITE_REVERB_*` in the bundle is only the fallback and is ignored here. Nothing is baked into `public/build` for the e2e and no socket is relayed: the staff pages connect straight to `127.0.0.1:<reverbPort>` like a production dashboard would.

**The `chat` seed** (`seed: 'chat'`, `SEED_P4` in `e2e/global-setup.ts`, constants in `e2e/support/users.ts` and `chat-seed.ts`): the installer's administrator (`ADMIN`), the agents **Alice Carter** (serves Billing + General) and **Bob Mitchell** (Sales + General) with saved logins `role: 'alice' | 'bob'` (plus `admin`), the categories General / Billing / Sales, and the published, enabled widget **Acme Storefront**: domain `localhost:<host port>` (the customer site), the three categories, open around the clock (`hours.mode = always_online`), no greeting popup, routing `online` at 0 s + `away` at 20 s, queue timeout 45 s, pre-chat form as the default (name required). `readSeed(instance)` / the `seed` fixture return the widget key and ulid, the category ulids and the user ids (`<instance dir>/seed.json`, written by `globalSetup`).

**Actors** (`e2e/support/actors.ts`, the `actors` fixture): `actors.staff('alice' | 'bob' | 'admin', { presence, open, keepAlive, device })` is a browser context of its own with that person's saved login, the socket relay, a `StaffApi` (`actor.api`) and an `Inbox` (`actor.inbox`); `actors.visitor({ device, locale })` is a context with no login and its own client address (`X-Forwarded-For` is added to every request to the app; the server trusts it in these scenarios, because chat starts are limited to 3 a minute per widget and network, and queued chats to 3 per network, so every visitor must be a network of its own). `device: 'project'` (default) takes the viewport of the running project (desktop 1280x800, mobile Pixel 7), `'desktop'` forces 1280x800. Every actor is watched (`watch.ts`): the fixture fails a passing test when a page threw, logged a console error, had a request fail or got an HTTP 5xx (`actor.watch.allow(/pattern/)` for the ones a spec provokes; `watch.statuses` lists every API status seen, `watch.known` the tolerated known issues, see below).

**What spec writers must know**

- **The scenario is shared by every test of a spec file and by the files that use it** (one server per project): presence, capacity and queues persist. Set presence explicitly at the start of a test (`actors.staff('alice', { presence: 'online' })`; a spec that needs nobody reachable sets both agents `offline`), identify chats by their ulid (never `toHaveCount` on the whole queue), end or close what you start, and give a spec file that changes presence or leaves chats open its own scenario (more `p4-*` entries; the ports are reserved). Playwright retries once: a failed first attempt leaves its chats behind.
- **Presence before the widget opens**: the panel re-reads availability when it opens, so set Alice/Bob `online` before `openCustomerSite(..., { open: true })` (a cached answer is dropped when an agent becomes reachable). Billing is served only by Alice, Sales only by Bob, General by both.
- **Who may read what** (`403` is not a bug): an agent sees a chat only while it is assigned to them or they hold an open offer; a `missed` or someone else's chat is `403` for an agent. Read such chats with `adminApi` / `actors.staff('admin')`.
- **One open chat per visitor** and a 10 s cooldown after a visitor cancels a queued chat: a new `actors.visitor()` is a new visitor.
- The dashboard is built for the e2e Reverb address: after a plain `npm run build` the next e2e run rebuilds (about a minute). The output of the servers (app, customer site, Reverb) is discarded; for Reverb's log run `php artisan reverb:start --debug` by hand with the scenario's environment (`instance.env`) on a free port.
- The inbox is a list -> detail drill-down on a phone: `Inbox.accept()` ends on the conversation, the queue is on the list screen.
- `Panel.startChat()` returns `status: 409` / `ulid: null` when the widget answered `no_agents` (the panel shows the offline form).

### P4 staff specs (E2): worlds, helpers and what to know

**Worlds.** The `p4-staff` server is shared by every `staff-*`, `security-*` and `realtime-outage` spec and Playwright runs files in parallel, but presence, queues and capacity are global to a scenario. So no test uses the seeded Alice / Bob: `createWorld(adminApi, instance, { categories, agents })` (`world.ts`) creates, through the management API, the test's own categories, agents (`world.agents.ann`, password `PASSWORD`) and a widget configured like Acme Storefront (open around the clock, `online` at once + `away` at 20 s, 45 s queue timeout, domain `localhost:<host port>`). Routing offers a chat only to agents who serve ITS category, chat starts are budgeted per widget and the widget key is the visitor's entry, so nothing a test does is visible to another. Assert by ulid, never by a total (the history page is scoped with its widget filter); tickets without a topic are visible to every agent of the scenario, so no test counts tickets. `startChat(rig, options)` (`staff-flow.ts`) is the usual start: a world, an agent online in the inbox, a visitor who started a chat from the real panel and (default) the agent's Accept.

### Rules of the suite

- **Web-first assertions only**; no `waitForTimeout`. Colour measurements (axe, screenshots) call `settle()` first: CSS transitions/fade-ins are 150-300ms and give false contrast failures if measured mid-way.
- Fortify throttles the login form (5 attempts a minute per email) and the setup-token form (5 a minute per IP): specs that type credentials use their own accounts per project (`loginAccounts()`), everything else starts from a saved session.
- Test accounts, the setup token and the `APP_KEY` are throwaway values that only exist in the `chatfeature_e2e*` databases/servers.
- `E2E_ONLY=installed,fresh-token npx playwright test ...` starts only those scenarios (handy while writing a spec; mode-2 specs need their `*-pizzasys*` scenarios in the list, which also starts the harness). Unknown extra env: `E2E_DEBUG=1` (APP_DEBUG), `E2E_PHP` (php binary), `E2E_HARNESS_DIR` (the pizzasys harness).
- **Mode-2 specs share the one harness**: nothing but `portal-outage.spec.ts` may stop it, and that spec runs alone in the last project (`pizzasys-outage`, which depends on `desktop` and `mobile`; run it by itself with `npx playwright test --project=pizzasys-outage --no-deps`). Specs only ever change the suite's own `e2e.roles.*` accounts upstream and restore them. Revocation and role-change specs lower `auth.pizzasys.verify_ttl_seconds` to its minimum (15 s) and poll, so each takes about 20-30 s.
- `browser.newContext()` inherits the saved session of `test.use({ role })`: pass `storageState: { cookies: [], origins: [] }` for a signed-out second browser.
- Type-check the suite with `npx tsc -p e2e/tsconfig.json`.
- **Run a subset with `--project=desktop --project=mobile`** (or one of them): without it `pizzasys-outage` and its dependencies (all of `desktop` and `mobile`) are loaded too, which needs the pizzasys harness files (`../chatFeature.harness`, not there in a git worktree: `E2E_HARNESS_DIR`).

### Add a scenario or a spec

1. Scenario: add an entry to `DEFINITIONS` in `e2e/support/scenarios.ts` (`kind`, a free port in 8110-8119, a `dbSuffix` -> `chatfeature_e2e<suffix>`, `mode: 'local' | 'token'`, optional `locale`, `perProject` for stateful ones; chat scenarios: `seed: 'chat'`, `hostPort`, `reverbPort` (and `perProject.mobileReverbPort`), `env: { TRUSTED_PROXIES: '*' }`, ports from the P4 ranges) and the name to `ScenarioName`. Nothing else: the `webServer` list, the reset, the install and the saved logins are derived from it.
2. Spec: `e2e/<area>/<name>.spec.ts`, `import { expect, test } from '../support/test'`, `test.use({ scenario: '<name>' })` (+ `role: 'admin' | 'agent'` for installed scenarios). Stateful flows: one ordered test or `test.describe.configure({ mode: 'serial', retries: 0 })`.
3. Prefer `data-testid` selectors (the contract with the frontend; the login/confirm/logout buttons use the kit's `data-test`).

### Known issues the watch tolerates

`e2e/support/watch.ts` lists product bugs that would fail every spec which finishes a chat (`KNOWN_ISSUES`; they are collected in `watch.known`, not reported as problems). Delete the entry when the product is fixed.

- **Visitor panel, console error on every ended chat**: `WebSocket is already in CLOSING or CLOSED state.` The panel closes its socket when the chat ends (`resources/js/lib/realtime/visitor/echo-socket.ts`, `close()`: `echo.leave(name)` then `echo.disconnect()`), and pusher-js still sends `pusher:unsubscribe` while the socket is already `CLOSING`. Harmless to the visitor, but it lands in the console of every customer's site.

## Gate checklist (end of every phase)

1. `composer test` (pint + larastan + phpunit), `tsc`, lint, Vitest, `npm run e2e` all green.
2. `/code-review` at high effort; fix findings.
3. `/security-review`; fix findings.
4. `/simplify`.
5. Update `CLAUDE.md` (via `claude-md-management:revise-claude-md`), the README roadmap checkboxes, the relevant `docs/*.md` and `docs/changelog.md`.
6. Commit `phase-N: <summary>` and tag `v0.N.0`. No push unless asked.
